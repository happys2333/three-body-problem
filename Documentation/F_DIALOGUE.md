# 统一 F 键提问

2026-10-31：按住 F 说话，松开后转写并自动提问。取消预设问题、人物选择和 V 键录音入口；正常语音交流时收起文字框，仅在麦克风或转写不可用时展开替代输入。

2026-11-02：玩家可在“操作与声音”中关闭麦克风或指定输入设备。关闭后 F 打开文字交谈，不启动录音或请求授权；Enter 始终可用。所选设备断开时提示改选，不暗中切换麦克风。见[麦克风设置](Settings/2026-11-02/README_CN.md)。

## Unity 负责的规则

- 每次按下 F 时，重新查询当前场景中有效、可交谈的人物。只有一个人时由该人物接收；多人时优先选择视野内未被遮挡、与视线夹角最小的人物，夹角接近时取距离较近者。没有可见人物时仍以视线最接近的有效人物接收，不设固定交谈距离。
- 接收者在录音开始前锁定。录音、转写或等待回答时转头、走远、经过剧情阶段切换，都不会把同一句问题改投给别人。
- 新一次 F 提问会中止上一次待处理的提问和声音。暂停、关闭对话、切出应用时取消采集；旧转写结果不能提交到新的一轮。原目标失效时取消，不暗中改选别人。
- 不因烈日、开场问答计数或普通剧情阶段禁止提问。标题、暂停、观察簿、总结、场景加载和调试预览不采集录音。
- 宫廷／质询只有收到有效的任务推进决定并播完回答才继续；寒暄、澄清或服务失败不算完成任务。明确使用离线剧情时，可在交流界面点“继续演出”。F 始终用于提问。

## LLM 负责的判断

是否明确向另一位人物提问，由 LLM 结合整句话理解。Unity 和网关不使用姓名关键词或正则表达式决定转交。普通提及、询问他人的情况、引用他人的话，不应自动改换接收者。

Unity 向 `/dialogue` 提供最初接收者 `recipientId`、原始 `utterance`、本角色的独立 `history`，以及在场人物名单 `interlocutors`。名单的 `id` 唯一标识人物实例；`npcId` 指定角色人格，`displayName` 和 `aliases` 帮助模型理解称呼。

正常回答：

```json
{"speech":"角色的回答","gesture":"talk","storyIntent":"continue","targetId":"","conduct":"neutral"}
```

LLM 决定转交：

```json
{"speech":"","gesture":"think","storyIntent":"continue","targetId":"在场名单中的人物实例 id"}
```

转交时，网关强制清空原接收者的台词和剧情意图。Unity 再次验证目标仍然有效，用目标角色自己的历史重新请求回答；第二次请求 `allowHandoff=false`，不允许循环转交。原接收者不显示回答、不发声、不把这次问答写入自己的记忆。最终只有目标人物记住并回答这句话。

主要人物使用独立角色提示词。居民、朝歌卫兵和中世纪守卫共用 `bystander.txt`，各个实例的对话历史仍然隔离。项目现有主角包含姬昌／周文王、纣王、教皇、学者和达芬奇；姬发不是姬昌的别名，也没有被凭空加入当前场景。

## 角色扮演与上下文（2026-11-02）

每次请求先放公共交流规范与独立角色设定，再放本人物的历史，最后提供最新现场事实与玩家当前问题。人物需要承接已说过的称呼、来历和约定，回应实际问题与情绪；避免每轮重报身份、重复盘问、提前揭露世界真相或把全部上下文复述一遍。

主要人物的本轮交流按角色 ID 保存于进程内存，姬昌由戈壁进入朝歌后继续使用同一份记忆；其他人物不继承他的私聊。配角按场景和实例区分。开始新旅程或退出进程会清空，暂不做对话存档。原先每个场景最多 12 条消息的限制已移除，现按所选输入窗口裁剪最旧的完整问答。

Unity 按交谈对象提供当前职责、是否看得见玩家、可见伤情、遮挡和公开剧情事实。自己的剧情演出台词会记入亲历；附近无遮挡的角色可以记住听到的演出台词。自由 AI 私聊不自动广播。玩家观察簿、猜想和旧轮次记录不自动成为 NPC 知识；室内人物不会凭空知道看不见的天象细节。

设置支持 32K、128K 和 1M 输入窗口，默认 32K；它是发送相关记录的上限，不会自动填满，也不增加单次 NPC 台词长度。DeepSeek 使用官方 V4 分词器计数并预留输出和消息开销；其他兼容服务使用保守的 UTF-8 字节预算。模型本身仍需支持所选窗口。完整实现、安装与原生验证见[人物记忆与长上下文](Dialogue/2026-11-02/README_CN.md)。

## 接入与验证边界

本机语音识别仍由 Unity 录音、本机 ASR 转写。网关默认离线剧情回退。玩家在设置中选择兼容接口或 DeepSeek 并填写连接信息后，该次请求直接使用所选服务，不需要另外开启网关的 `--online`；`--online` 与服务端环境变量仅用于旧版网关配置。离线模式保留最初接收者，不假装理解点名意图。

网关测试使用模拟上游验证协议、静默转交、在场名单限制和单次转交；这不证明真实 LLM 对自然语言指向的准确率。Unity 测试覆盖视线选择、距离与遮挡、对象锁定和旧结果拒绝。真实麦克风权限、现场噪声和真实模型的语义效果需要单独实测。独立 `.app` 已随 2026-11-02 上下文改动重新构建；F 键初次验收见 [2026-10-31 记录](Dialogue/2026-10-31/README.md)，本次结果见[最新验证](Dialogue/2026-11-02/README_CN.md)。

2026-11-02 已用 Discovery 的 `Atria-Dawn` 完成[初次实测](Dialogue/AtriaAudit20261102/README_CN.md)，随后实现了[受限决策与实际卫兵玩法](Dialogue/DecisionRuntime20261102/README_CN.md)。该入口的 NPC 请求关闭推理，保留 320 token 输出预算；所有人物的幕后词复述经过发声前过滤，戈壁仍有更严格的身份、知识和阶段边界。

## 当前决策协议

Unity 在 context 中提供 `decisionProtocol=1`、决策 revision、当前权威状态、卫兵可达性、呈表是否完成，以及 allowedStoryIntents。模型补充 conduct，区分普通提问、澄清、具体方案、同意安排、扰乱秩序、持续抗命、暴力威胁和道歉。advance 只在当前正确角色、呈表已完成、玩家给出具体方案或同意已有安排时有效；“能否查验”仍是提问，不自动推进。

纣王与教皇可先 warn。另一次交流中，玩家在明白警告后继续抗命或威胁，才可发出开放的 pursue（拘捕）或 attack（致命武力）。接受道歉或恢复合作时可 stand_down。其他人物没有统治者权限。网关过滤后，Unity 再校验当前阶段、revision、角色、行为类型和卫兵状态；模型没有直接修改血量、死亡或任意场景的字段。

卫兵使用两幕各自的烘焙导航，实际靠近、出矛，并通过距离和遮挡检查造成伤害。玩家生命值不显示；制服和死亡分别结束本次觐见并提供重试。重试回退到本章觐见前，恢复对应记忆检查点，保留戈壁相遇记录。演出期间玩家走到王座附近，也不会再被错误的同行等待条件卡住呈表。

网关返回受限 failureCode 区分离线模式、服务拒绝、超时、认证和额度等故障。在线失败会显示状态，不写入人物有效历史，不消耗戈壁回答次数，不生成新处置或推进决定。设置提供 60 秒等待的快捷选项。原始服务错误与凭据均不进入人物台词。
